## 0. 一句话定义

把「现在的我」（容易冲动、想即刻消费）和「未来的你」（要攒钱、要自由）拆成两个视角，用**规则引擎（去人格化的纪律引擎）**按既定数学规则，约束「现在的我」对资金的随意支配，实现「能力范围之内有钱花」。

本质：用一套固定的记账纪律，帮「未来的你」不被「现在的我」冲动透支——**这是一个个人自律记账 / 预算辅助工具，不是法律意义上的信托**。

> ⚠️ **性质声明（务必知悉）**：本框架**仅为个人自律记账与预算辅助工具**，**不具备任何法律效力**，不构成信托、托管、资产隔离或任何法律关系。资金始终由用户本人实际控制；下文「流程隔离 / 不可直取」仅指**软件内的流程审批约束（操作门槛），不代表法律上资产已隔离**。发生债务、离婚、继承、破产等情形时，本工具**不产生任何资产保护效力**。请勿将其理解为法律安排。

## 1. 权责关系映射（功能角色边界）

> 下表的「角色」只是**同一用户的不同视角**，用于解释规则分工，并非法律主体。

| 角色 | 个人映射主体 | 核心权力 | 不可推卸义务 | 行为约束红线 |
|---|---|---|---|---|
| 配置者（现在的我） | 当前用户（收入 / 资产录入方） | 初始化契约、切换数据模式、人工覆写审批、修改全部契约参数、导入 / 手动修正资产 | 如实上报资产、收入、负债、大额支出；知悉所有覆写行为对长期目标的负面影响 | 软件内所有支取应走审批通道；但用户现实中仍完全掌控资金，本工具无强制力 |
| 规则引擎（纪律引擎） | AI 规则引擎（无情绪、无偏好） | 自动核算资产、审批支取、月度校准目标、生成记账报表、触发冷静期、推送提醒 | 客观服务未来的你长期利益；审慎核算资金影响；完整留痕每一笔决策；不主动修改用户原始契约参数 | 无权直接修改契约核心配置；仅能提供调整建议；不可为短期消费牺牲长期资产底线 |
| 未来的你（长期视角） | 当下用户 + 未来各时间节点的自己 | 享受合规分配、申领里程碑奖励、提交申诉、查看全量资产记账报表 | 兼顾短期生活需求与长期财富目标，理性使用人工覆写通道 | 不允许无限制动用兜底覆写通道，避免框架失效 |

**关键机制：流程隔离（非法律隔离）**
- 在工具内，资产划入资金池后，所有资金流出（无论计划内 / 非计划内 / 奖励 / 人工覆写）**统一走规则引擎标准化校验流程**（**§4.4 统一判定逻辑** + §5.1 阈值 + 安全垫护栏），不得绕过。
- 这是一道**流程上的操作隔离**：在软件内不存在「直接取出花掉」的入口，唯有审批通道这一出口；配置者本人也须以「未来的你」身份走申领 / 覆写流程，并接受留痕与目标影响确认（§5.2 人工覆写兜底）。
- ⚠️ 重申：此隔离**仅为软件内流程约束，无法律效力**，不改变用户对资金的现实所有权与控制权，亦不构成资产隔离。其意义在于提高冲动消费的操作门槛，是框架对抗自我透支的根本护栏，也是 §5.2 兜底通道「非常态」定位的依据（覆写是例外出口，不是默认自由）。

### 2.0 通用计算公式汇总（全文复用）

全文档统一复用以下 8 个公式（含真实口径测算与审计快照），各章节不再重复推导，仅引用编号。**本次修订核心：引入净资产与月度净流入概念，所有测算基于「资产 - 负债 - 刚性年度支出摊」的真实现金流，解决静态资产测算失真。**

**公式速查索引**：

| 编号 | 名称 | 用途 | 关键依赖 |
|---|---|---|---|
| F0 | 净资产与月度净流入 | 一切测算的真实现金流基数 | corpus / liabilities / rigid_annual_expenses |
| F1 | 有效安全垫 | 审批底线（§4.4 场景判定） | safety_cushion 三模式 / F0 净资产 |
| F2 | 冷静期自动阈值 | 触发 §5.1 冷静期 | F1 / cooldown_days（含 clamp 护栏） |
| F3 | 月度可投增量（名义） | 延后/提前测算分母（乐观上限） | F0 月度净流入 / invest_ratio |
| F3.5 | 通胀回撤修正（真实月进展） | 落地测算默认口径 | F3 / calc_params |
| F4 | 目标落后度 lag | 校准触发（§6.2）/ 进度条（§6.1） | current_amount / deadline（含超期 clamp） |
| F5 | 消费影响（简化口径） | 意见书轻量展示（±20%~50% 误差披露） | F3 |
| F6 | 里程碑奖励额度 | §6.3 达成率≥120% 解锁 | current_amount / target_amount |
| F7 | 真实节奏测算 | 复利+通胀+回撤准则口径 | F3.5 / calc_params |
| F8 | 审批审计快照 | 每笔审批全中间变量落盘（§10.1） | F0~F7 全部 |

> 通用守卫（所有公式适用）：
> - 除零保护：任何分母出现 `0` 或缺省（`null`）时，结果按 `0 / 不适用` 处理，并在记账报表标注「数据不全，测算存在偏差」（与 §3 边界护栏一致），不输出虚假精确值。
> - 无 `deadline` 目标（如「生活质量」）：禁用公式 4 的 lag 计算，进度条仅展示攒钱占比（见 §6.1）。

**公式 0：净资产与月度净流入（修正静态失真）**
```
资产      = corpus                              // 资金池余额（资产侧）
负债总额  = Σ liabilities[].balance            // 所有负债余额之和
刚性月摊  = Σ rigid_annual_expenses[].amount / 12   // 年度刚性支出平摊到每月
负债月供  = Σ liabilities[].monthly_payment     // 既有固定负债月供（房贷/车贷等）
净资产    = 资产 - 负债总额
月度净流入 = monthly_contribution              // 已由用户填「税后收入 - 负债月供 - 刚性月摊」后的可自由支配净流入
```
> 说明：原设计把 `monthly_contribution` 当「纯增量」，会高估可投能力（忽略了月供与保费）。此处显式要求该字段为**已扣除所有固定刚性流出后的自由现金流**，负债与刚性年支出单独建账，使安全垫、延后测算落到真实可投基数上（解决硬伤「静态测算失真」）。

**公式 1：有效安全垫 `effective_cushion`**（基于净资产，防资不抵债时垫虚高）
```
if mode = "months": effective_cushion = living_baseline × months
if mode = "fixed":  effective_cushion = fixed
if mode = "ratio":  effective_cushion = max(净资产, 0) × ratio     // 用净资产而非资产，负债高时垫自动收敛
```

**公式 2：冷静期自动阈值 `effective_cooldown_threshold`**
```
effective_cooldown_threshold = (effective_cushion / 30) × cooldown_days
```
> 护栏：`fixed` / `ratio` 模式下安全垫体量可能极大或极小，阈值建议 clamp 到 `[living_baseline × 0.2, living_baseline × 3]` 区间——防止冷静期形同虚设（阈值过高）或事事触发（阈值过低）。

**公式 3：月度可投资增量（目标延后 / 提前测算分母）**
```
月度可投增量 = 月度净流入 × invest_ratio
```
> 若 `月度净流入 ≤ 0`（净流出/零结余），`月度可投增量 = 0`，公式 5/7 延后月数视为「无法在常规节奏内覆盖」，意见书须提示而非除零。

**公式 3.5：通胀与资产回撤修正系数（真实节奏护栏）**
```
年通胀率      inflation        // 用户可设，默认 0.025（2.5%）；目标 `target_amount` 按年通胀复利调增
回撤缓冲系数  drawdown_factor  // 投资类资产历史/设定年化回撤，默认 0.10；实际净增 = 名义增 × (1 - drawdown_factor)
实际月进展 = 月度可投增量 × (1 - drawdown_factor) × (1 + (r_gross - inflation) / 12)   // 年差率折月（月增量只叠加当月收益差），含通胀侵蚀与回撤
```
> 说明：真实攒钱节奏受「通胀抬高目标额」+「投资回撤吃掉名义收益」双重蚕食。公式 3 是名义口径（乐观上限），公式 3.5 是保守真实口径（落地测算默认用它）。`target_amount` 在测算时按 `target_amount × (1 + inflation)^(剩余年数)` 动态折算，避免「攒够数字却因通胀不够花」的隐性失真。

**公式 4：目标落后度 `lag`**（依赖 `current_amount`，已补字段）
```
若 deadline = null：禁用本公式（仅展示攒钱占比）
总周期天数 = deadline - start_date
已过天数   = 当前日期 - start_date
时间进度   = 已过天数 / 总周期天数
达成进度   = current_amount / target_amount      // current_amount 见 §2 schema（已补）
时间进度   = min(时间进度, 1)                   // clamp：超期目标时间进度封顶 1，lag 有界
lag        = 时间进度 - 达成进度
lag > 0 表示目标落后
```
> 超期守卫：当前日期 > deadline（已超期未达成）时不再参与 §6.2 月度校准（校准假设「还有时间可调」已失效），转入 §6.4 目标生命周期处理。

**公式 5：消费对目标影响测算（标注简化误差风险）**
```
若 月度可投增量 = 0：延后/提前月数 = 不适用（标注「当前无自由现金流覆盖」）
// 简化口径（保守、无复利，意见书默认展示）
延后月数 = 申请支出金额 / 月度可投增量
提前月数 = 撤回金额   / 月度可投增量
// 真实口径（含复利+通胀+回撤，见公式 7）
真实延后月数 = 公式 7(申请支出金额)
```
> ⚠️ **简化误差风险标注**：公式 5 的简化口径是「线性、无复利、无通胀、无回撤」的乐观/保守边界估算，实际达成受投资收益复利、通胀侵蚀、资产回撤影响，误差可达 ±20%~50%（尤其长周期目标）。意见书与报表须以「约 / 大约 / 估算」措辞呈现，并附「长期目标以真实口径（公式 7）为准」提示，不得给出虚假精确值。

**公式 6：里程碑奖励额度**（依赖 `current_amount`）
```
超额资产 = current_amount - target_amount        // current_amount 见 §2 schema（已补）
达成率   = current_amount / target_amount
if 达成率 >= 1.2 && reward_unlocked = false:
    reward_max = 超额资产 × 0.2                  // 奖励上限 = 超额部分的 20%（天然不超超额本身）
```

**公式 7：真实节奏测算（复利 + 通胀 + 回撤，落地测算口径）**
```
// 以「实际月进展」（公式 3.5）为净增，对目标缺口做现金流测算
剩余年数 = max((deadline - 当前日期) / 365, 0)     // deadline=null 时禁用本公式（同公式 4 守卫）
目标缺口_nominal = target_amount × (1 + inflation)^剩余年数 - current_amount   // 通胀动态折算后缺口
净月增 = 实际月进展                                 // 直接复用公式 3.5，同一口径不重复定义
剩余覆盖月数 = 目标缺口_nominal / 净月增            // 按当前真实节奏还需攒多少个月
真实延后月数 = 申请支出金额 / 净月增                // 本次支出使目标推迟的月数（真实口径）
真实提前月数 = 撤回金额 / 净月增
```
> 说明：公式 7 引入复利增长（净月增本身已含收益再投资）与通胀动态折算，替代公式 5 的线性近似，消除长周期目标「攒够数字却不够花 / 低估复利加速」的双重偏差。仍保留公式 5 作轻量展示，二者差异在报表中可并列呈现。

> **全文误差风险声明**：所有「延后/提前月数」「达成率」「奖励额度」均为**基于输入的测算值**，非承诺。变量（通胀率、投资收益率、回撤系数、收入稳定性）任一失真即导致偏差；本工具定位为纪律辅助，不替代专业财务规划。每次审批的**完整计算中间变量**落 `approval_log`（见 §10.1 / 公式 8），支持事后完整复盘验算。

**公式 8：审批审计快照（完整中间变量，支持复盘验算）**
```
approval_log 每笔记录须含：
  time, amount, category, scene                 // 基础事实
  inputs: { corpus, liabilities_sum, rigid_sum, monthly_net,              // 公式0 中间变量
            net_assets, invest_ratio, monthly_invest_nominal,             // 公式3
            inflation, drawdown_factor, r_gross, monthly_invest_real,      // 公式3.5
            effective_cushion, monthly_baseline,                          // 公式1
            target_amount_adj, gap_nominal, net_monthly,                   // 公式7
            lag, lag_streak }                                             // 公式4
  formulas_used: ["F0","F1","F3","F3.5","F4","F5/F7"]   // 实际引用公式编号
  decision: { scene: A|B|C, result: 批准|附条件|驳回, summary }
  alt_plan: <§5.3 替代方案文本>
```
> 说明：每笔审批把本次计算用到的**全部输入与中间变量**按公式编号落盘，复盘时可逐式重算核对（如「为何判 C」「延后月数怎么来的」），杜绝「黑盒裁决」。

### 2.1 安全垫计算逻辑（三模式可切换）

`safety_cushion.mode` 决定有效安全垫 `effective_cushion` 的算法（即**公式 1**，用户按自身情况自选）：

| 模式 | 算法 | 适用 | 联动性 |
|---|---|---|---|
| `months` 月数锚定（**推荐默认**） | `effective_cushion = living_baseline × months` | 绑定月度基础生活费，随收入、生活成本自动浮动，适合**绝大多数工薪、现金流不稳定人群** | 随 `living_baseline` 自动调整，免频繁改 |
| `fixed` 绝对数 | `effective_cushion = fixed` | 固定绝对金额安全垫，适合**高稳定高薪、无大额消费波动人群** | 手动设定，不变 |
| `ratio` 比例动态 | `effective_cushion = max(净资产, 0) × ratio`（公式 1） | 按净资产比例动态调整，适合**资产体量较大、长期理财人群** | 随净资产自动浮动（负债升高时垫自动收敛） |

> **默认推荐 `months`**：对工薪 / 现金流波动群体最友好——安全垫随真实生活费走，既不因收入涨而闲置、也不因通胀悄悄击穿。仅当你明确属于高稳定高薪或大体量理财人群，才考虑 `fixed` / `ratio`。

切换示例：早期用 `months`（现金流优先），资产做大后切 `ratio`（保比例不放手）。

## 3. 数据来源 —— 混合开关（核心决策）

三种模式，由 `mode` 字段切换：

- **ledger 持久台账**：skill 维护真实账本。每次收入 / 支出上报，更新 `corpus`。审批基于真实余额 + 历史趋势。强，但需持续记账。
- **conversational 对话式**：不存长期账。每次口头给数（"本月剩8000，想花3000买X"），当场审，审完即弃。零维护，轻。
- **hybrid 混合（默认推荐）**：资金池 / 目标 / 注入额走持久台账（必须准，是护栏基础）；日常消费请求走对话式临时审（不强制逐笔记账）。开关随时切。

切换示例：平时 hybrid；月底做记账报表时临时切 ledger 看真实累计。

**三种模式能力对比**：

| 模式 | 资产台账持久化 | 日常消费记录 | 记账负担 | 适用人群 |
|---|---|---|---|---|
| `ledger` 全台账 | 完整持久存储 | 逐笔强制记录 | 高 | 理财精细化、有长期记账习惯用户 |
| `conversational` 对话 | 临时不长期留存资产数据 | 单次会话临时计算，会话销毁即清空 | 极低 | 临时试用、不愿记账、短期使用 |
| `hybrid` 混合（默认） | 资金池、目标、月度注入持久保存 | 消费审批支持口头临时上报，非强制逐笔入账 | 中等 | 绝大多数长期使用用户（平衡精度与负担） |

**模式边界护栏**（数据完整性与信任边界）：
- `ledger` 模式：若缺失历史流水（早期未记录 / 导入断裂），报表必须标注 **「数据不全，测算存在偏差」**，不假装精准；缺失期间的目标进度、趋势图以「不完全样本」呈现，提示用户补录。
- `conversational` 模式：无持久资产台账，**每次审批必须由用户手动确认当前总资产**（规则引擎不能凭空取数）；未确认则审批中止，不进入判定式。
  - **审计不豁免**：「审完即弃」仅指**资产数据**不持久；审批结论本身（时间/金额/类目/判定/当次用户口头确认的资产数）仍落 `approval_log`（§10.1 永久仅追加）——数据轻量化不等于决策无痕。
- `hybrid` 模式：资金池资产为**核心基准**（持久、权威），临时消费数据仅作单次审批参考，**绝不修改底层 `corpus`**；只有正式收入 / 注入 / 经审批的支取才更新 `corpus`。

### 3.1 模式切换平滑过渡（防弃用）

记账负担会随时间变化，硬切模式易致放弃。在 `hybrid` 下自动监测用户记账行为，触发温和切换提示（**仅提示，不自动改 mode**，用户终裁）：

| 触发条件 | 提示动作 | 目的 |
|---|---|---|
| `hybrid` 下**连续 7 天**主动上报消费记录 | 提示「你已连续 7 天记账，是否切到全 ledger 持久台账，让规则引擎看得更准？」 | 行为已稳定 → 升级精度 |
| `hybrid` 下**连续 14 天**无完整账目上报 | 提示「最近没怎么记账，可轻量化切回对话式，避免繁琐放弃使用」 | 防因为繁琐直接弃用 |

**实现要点**：
- 监测字段（写 `contract.json`）：`last_report_date`（最近一次完整上报日）、`report_streak`（连续上报天数计数器，断则归零）、`gap_streak`（连续缺报天数计数器，报则归零）。
- 仅 `hybrid` 模式触发；`ledger` / `conversational` 已定态不弹提示。
- 提示为软建议：`记账切模式 ledger|conversational` 由用户主动确认才生效，保持「规则引擎只建议、配置者掌握开关」的自律纪律。
- 计数器随每次上报 / 报表生成更新；跨日判断用自然日。

### 3.2 hybrid 模式定期自动对账（消除资产数据漂移）

**问题**：hybrid 是默认模式，资金池走持久台账、日常消费走对话式临时审。若长期不核对，持久 `corpus` 与现实账户（收入入账、已发生固定支出、投资市值波动）会逐渐**脱节漂移**，导致安全垫、目标进度测算建立在失真基数上。

**方案**：hybrid 下规则引擎按 `reconcile.period_days`（默认 30 天）周期性发起**对账提醒**，把持久 `corpus` 与现实资产对齐。

| 对账状态 | 触发 | 动作 |
|---|---|---|
| 距 `last_reconcile` 满 `period_days` | 主动推送「请核对本月资金池：当前记录 ¥X，现实账户是否一致？」并附近月差异提示 | 用户确认 / 修正 `corpus` 与 `liabilities` / `current_amount` 后写入，更新 `last_reconcile` |
| 连续 `reminder_streak` 超阈值（默认 2 次未对帐） | 提示「长期未对账，数据可能已漂移，建议切回 conversational 避免错误审批」 | 复用 §3.1 降级逻辑，不强制 |

**护栏**：
- 对账为**软提醒 + 用户确认**，规则引擎不自动改写 `corpus`（遵守 §10.3 最小权限）；差异由用户拍板。
- 对账差额不进入审批判定历史；仅同步真实基数，使 §4.4 / §6 测算回到真实现金流（呼应 §2.0 公式 0）。
- `ledger` 模式因逐笔记账自带对账属性，不触发本机制；`conversational` 无持久台账亦不触发。

## 4. 规则引擎职责（自律纪律 + 统一判定逻辑）

### 4.1 审慎原则

- **大额支出强制测算**：对长期目标延后影响（按 **公式 3 + 公式 5**）必须写入审批意见书，不得豁免。
- **突破安全垫的支出**：默认「附条件 / 驳回」，不允许无限制透支缓冲资金（即安全垫只可被临时、可控地触碰，不可作常规宽松口子）。
- **月度自动校准**：对连续落后的目标（见 §6.2 校准缓冲期），适度收紧非计划消费审批——滞后越深，护栏越紧。

### 4.2 长期优先原则（核心护栏）

- 规则引擎**仅服务长期综合收益**，必须驳回损害未来的你长期资产的冲动请求。
- **不受用户当下短期诉求干扰**：无论用户如何强调「就这一次」「真的很需要」，规则引擎只认契约 + 安全垫 + 目标进度，这是整个框架的核心约束。
- 这是对抗「现在的我剥削未来的我」的根本闸门——长期优先原则优先于用户临时意愿。

### 4.3 分账隔离原则

- 资金池资产与日常灵活消费账户**账面物理隔离**（逻辑上分账，不混入同一流水）。
- 任何消费支取**均从资金池扣除**，禁止混同记账；日常消费账户仅作展示/过渡，不得成为绕开审批的暗道。
- 与 §1「流程隔离」呼应：隔离是物理前提，流程隔离是权限前提，二者共同构成资金安全底座。

### 4.4 支取审批统一判定逻辑（整合简化，全局唯一标准）

> 全文档任何审批（计划内 / 计划外 / 奖励 / 白名单 / 覆写）**统一走本判定逻辑**，不再各自为政。

**输入**：当前 corpus（资产侧余额）、current_amount（各目标累计，见 §2 schema）、申请支出金额、消费类目、是否计划内

```
场景 A：corpus - 支出 >= effective_cushion（公式 1，基于净资产口径）
        且 不恶化 objectives 目标进度（公式 4 的 lag 不增大，current_amount 口径）
        → 直接批准，合理享受额度正常使用

场景 B：corpus - 支出 < effective_cushion
        但 月度净流入（公式 0）可覆盖缺口
        → 附条件批准（分期 / 延迟支取 / 缩减金额）

场景 C：击穿安全垫 且 无月度净流入兜底
        或 严重拖慢目标达成（lag 显著增大 / 损害长期资产底线）
        → 驳回 + 配套替代消费方案（见 §5.3 意见书）
```

说明：
- 场景 A 是「能力范围之内有钱花」的常态放行区。
- 场景 B 的白名单（§5.1.2 医疗/应急）可免冷静期，但仍须通过本判定（不豁免安全垫校验）。
- 场景 C 触发时，意见书必须给出正向替代方案（§5.3），让驳回可操作而非空拒。
- **口径统一声明**：本判定中「资产 / 余额」均指 corpus（资产侧，单位元），安全垫 effective_cushion 在 ratio 模式下基于**净资产**（公式 0），负债升高时自动收敛，不虚高（见 §2.0 公式 1）。

## 5. 审批决策引擎

- **触发**：自然语言 "审查：买X花Y" 或 `记账审批 <描述>`
- **输入**：请求金额、类目、是否计划内、当前 corpus（依 mode 取数）
- **输出**：**批准 / 附条件 / 驳回** + 审批意见书（见 §5.3，含契约对照 + 安全垫 + 目标影响 + **正向替代方案**）
- **判定基准**：所有结果统一走 **§4.4 统一判定逻辑**（场景 A 放行 / B 附条件 / C 驳回）。
- **冷静期**：`支出 > effective_cooldown_threshold`（§5.1 阈值，按 **公式 2**）且**不在极速白名单**时自动进入 3 天复核，期间可撤回 / 申诉。
- **兜底**：被驳回可申诉，连续 3 次驳回开放一次人工覆写（见 §5.2）。

### 5.1 冷静期机制分层优化

**触发条件**：`申请金额 > effective_cooldown_threshold`（阈值按 **公式 2** 自动联动，默认 `"auto"`），且**不在极速白名单**（见 §5.1.2）；默认冷静 **3 自然日**。

**双阶段预警提醒**（降低遗忘 / 重复冲动）：

| 时点 | 动作 | 目的 |
|---|---|---|
| 冷静期第 1 天 | 告知「申请 Y 待审核，冷静期还剩 N 天」，避免重复提交冲动请求 | 冷却起始锚定，防重复申请 |
| 到期前 1 天 | 二次确认「申请 Y 明日到期，确认执行 / 撤回？」 | 到期前给终裁窗口，防遗忘自动过期 |

- 若用户在任一时点**主动撤回** → 触发 **§5.1.1 撤回正向激励**，冷静期结束。
- 若满期无撤回且未申诉 → 按 §4.4 进入规则引擎终裁（批准 / 附条件 / 驳回）。
- **状态持久化**：进入冷静期的申请落 `pending_requests[]`（schema 已含：request_id / 金额 / 类目 / 到期时间 / 状态），**跨会话不丢单**；状态机 `cooling → withdrawn | decided | expired`，提醒调度依据 `expire_at` 计算，申诉计数按 `request_id` 关联（§5.2）。

#### 5.1.1 撤回正向激励（强化自律）

用户主动撤回冲动申请时，不只用「已驳回」收尾，而是**换算「提前达成目标时长」正向反馈**，把「忍住没花」折算成长期收益：

```
本次撤回帮你多攒下 = 撤回金额（即原申请额，未支出）
目标进度提前 ≈ 撤回金额 / 月度可投增量   （按 **公式 5** 提前月数，保守不计复利；月度可投增量见 **公式 3**）
```

文案示例：「✅ 你撤回了 1 万元冲动申请，等于多攒 1 万；按当前攒钱节奏（月度可投增量约 5 千），FIRE 进度提前约 2 个月。规则引擎替未来的你谢谢你。」
- 与 §5.3「延后时长」算法同源，形成「花了=延后 / 忍住=提前」对称认知；即使撤回的是本就会被驳回的申请，仍给正向激励——重点奖励自律行为本身。
- 正向反馈仅作感知强化，不改契约字段。

#### 5.1.2 白名单极速通道（含单笔 / 年度额度上限）

医疗、急诊、房屋应急、车险理赔等刚需场景**免冷静期**，触发时即走 §4.4 校验 + 即时审批，**仅跳过 3 天等待流程**；所有极速审批日志**单独标记 `fast_track:true`** 审计。

**额度上限护栏（防无限透支安全垫）**：
- `fast_track_whitelist` 每项结构为 `{ name, per_tx_cap, annual_cap, used_annual }`（schema 见 §2）：
  - `per_tx_cap`：单笔极速审批金额上限；
  - `annual_cap`：该场景年度累计极速审批上限；`used_annual` 年度累计已用，跨年归零。
- **判定顺序**：申请金额 ≤ `per_tx_cap` **且** `used_annual + 申请金额` ≤ `annual_cap` → 走极速通道（免冷静期，仍过 §4.4）；任一超限 → **降级为常规审批**（走冷静期 + 全套判定），防止白名单被当成无限透支口子。
- 每次极速放行后 `used_annual += 申请金额`，并在记账报表标注剩余年度额度。

- 白名单由 `记账白名单 加/删 <场景> [per_tx_cap] [annual_cap]` 管理；新增项须显式给双上限，否则拒绝写入。
- **护栏**：仅免等待，**不豁免安全垫校验与 §4.4 判定**（突破 `effective_cushion` 仍走附条件 / 驳回）；建议仅纳入真实刚需，不纳入「合理享受」类目，避免架空冷静期。

### 5.2 申诉 + 人工覆写兜底流程（边界加固）

**问题**：§4.4 判定 + 冷静期 + 校准构成刚性护栏，可能误判真实合理的特殊需求（一次性大额学习投资、家庭重特大支出），纯自动驳回会让用户感到被「规则绑架」。
**方案**：驳回后可申诉，连续 3 次申诉被驳触发一次**人工复核覆写**入口，由配置者（用户本人）亲自裁决。

**流程**：
1. 驳回后 `记账申诉 <理由>`；规则引擎按 **§4.4 统一判定逻辑**重审，仍不达标则维持驳回（`appeal_count += 1`）。
2. 同一需求**连续 3 次申诉驳回**（`appeal_count >= 3`；申诉与原申请以 `request_id` 关联，计数按同一申请累计、换申请自动归零）→ 开放一次性人工复核权限，提示「你已连续 3 次申诉被驳，现开放一次人工复核——请作为配置者亲自裁决」。
3. 人工覆写时**必须确认知悉本次消费带来的目标延后时长**（联动 §5.3 延后算法），写入 `contract.json` 的 `override_log`（时间、金额、目标延后影响、确认语）。

**护栏**：
- 单次人工覆写**消耗申诉计数**，计数归零；需重新积累 3 次申诉才可再次开启兜底通道——防兜底被当常规通道。
- 人工覆写**仅作用于当次支取**，不修改 `objectives.weight` / `safety_cushion` 等原始契约结构，不破坏整体自律纪律。
- 所有 override 进 `override_log`，月度报表单列「本期人工复核次数与影响」，保持透明可审计。
- 与 §5.1.2 极速白名单互补：白名单是「提前约定免等待」，兜底通道是「事后申诉破例」，双保险覆盖刚需与特殊合理需求。

### 5.3 标准化审批意见书（弱化说教，优化文案逻辑）

**固定三段式 + 正向替代方案**，**驳回 / 附条件场景强制输出**：

1. **契约对照**：当前资金池、安全垫余量、本次支出是否击穿底线（依据 §4.4 场景判定）。
2. **长期目标影响**：精确折算对应目标**延后月数**（按 **公式 3 + 公式 5**，保守无复利；选取最相关目标 = 按 objectives 权重 / 落后度 lag 优先）。
   例：「本次 1 万元非必要消费若获批，FIRE 目标达成时间将延后约 2 个月」。
3. **合规替代方案（优先级从高到低）**：
   - 从月度「合理享受」固定额度拆分支取（不破垫、不损目标）；
   - 拆分多月度分期支取，不击穿安全垫；
   - 等待目标超额里程碑（§6.3）解锁奖励额度后支取。

**文案基调**：客观测算代价、提供可行路径，而非单纯拒绝。「规则引擎不是不让你花，是帮你算清代价后选更好的花法」。

**意见书模板（驳回示例）**：
```
【规则引擎意见】驳回：买 X 花 1 万（非计划内·突破安全垫）
· 契约对照：corpus 扣 1 万后跌破 6 个月安全垫
· 目标影响：FIRE 达成延后 ≈ 2 个月（真实口径约 2.4 个月，含通胀/回撤，见公式 7）
· 替代方案：分 3 个月从每月「合理享受」额度支取（每月约 3333，不破垫不损目标）
· 你可在冷静期内申诉，规则引擎按 纪律义务终裁
```

### 5.4 契约核心护栏修改二次确认 + 风险提示（防冲动改规则）

**问题**：`记账自定义` 可改任意契约参数，若用户情绪低落 / 冲动时把 `safety_cushion` 调低、`invest_ratio` 调 0、删目标，等于亲手拆掉自己的护栏，且事后无感。
**方案**：对**核心护栏字段**的修改引入「二次确认 + 风险提示 + 冷静窗」三道闸门，与支出冷静期（§5.1）同源但作用于「改规则」本身。

**核心护栏字段（受二次确认约束）**：
- `safety_cushion`（任一子项）、`invest_ratio`、`objectives[].target_amount` / `deadline` / `weight`、`living_baseline`、`fast_track_whitelist`、`calc_params`、`optimization_goal` 切换至 `wealth`/`objective` 收紧态。

**流程**：
1. 用户发起上述字段修改 → 规则引擎**先回显「修改前 vs 修改后」对比**，并标注影响（如「安全垫由 6 月降至 2 月，抗风险能力大幅下降」「invest_ratio 归零，FIRE 将实质性停滞」）。
2. **二次确认**：要求用户显式回复「确认修改」或等价指令，单次确认不生效（防误触 / 手滑）。
3. **冷却窗（可选收紧）**：对 `safety_cushion` 下调、`invest_ratio` 下调等「削弱自身」的修改，额外给 **1 个自然日**冷静窗，窗内可无理由撤回，到期前二次提醒（复用 §5.1 二次确认机制）。
4. 确认通过后，修改**落契约 + 写 `override_log`**（标注「契约参数人工修改 + 影响摘要 + 确认语」），保持可追溯（与 §10.1 审计一致）。

**护栏**：
- 非核心字段（如 `allowed_categories` 微调、`mode` 数据模式）走普通确认，不强制二次确认 / 冷却窗，避免体验过度摩擦。

> ⚠️ **`allowed_categories` 实现现状（2026-07-28 更新）**：已补专用开关 `customize --add-category 名` / `--remove-category 名`（去重追加 / 移除缺失报错），不再需要整表替换。该字段**嵌套于 `distribution_rules`**（已在 `FIELD_ZONES` 注册为 CONFIG 护栏字段），故专用开关直接复用 §5.4 二次确认、**不触发冷却窗**（因不改 `invest_ratio`）。**已落地选项 A**：`judge` 仍**不校验** `--category` 是否落在表内——保持自由文本 + 词汇表作推荐。选项 B（补开关 + `judge` 强制校验，超纲类目直接驳回、须先 `--add-category`）尚未实现；若需开启，开关侧已就绪，仅需给 `judge` 加一步成员校验。此与「极速审批类目」(`fast_track_whitelist`，有专用 `--whitelist-add/-remove`) 仍是两回事，命名易混淆。
- 风险提示须用具体数字与后果，不空泛「此操作有风险」；让用户**看清代价**而非被劝阻。
- 与 §5.2 人工覆写同源：都是「人最终掌权，但必须看清算衡、留痕可审计」，杜绝静默拆护栏。

## 6. 记账报表 `记账报表`

资产池、分配进度、目标达成率、本月已批 / 驳回统计、安全垫余量预警。

### 6.1 报表双可视化组件优化

纯文字数值难以建立「节奏感」，在报表中补充两类可视化组件，比纯数据感知更强。

**1. 长期目标双轨进度条**
- 每个 `objective` 渲染一条进度条，双轨对照：
  - **达成进度** = objective.current_amount / target_amount（实填部分，字段见 §2 schema）
  - **时间进度** = 已消耗周期 / 总周期（参照基线，虚线标记）
- **颜色标识**（直观感知状态）：
  - 超前 → 绿色（达成进度 ≥ 时间进度）
  - 小幅落后 → 黄色（落后但 `lag` 仍在可接受窗）
  - 严重落后 → 红色（触发 §6.2 校准缓冲阈值）
- **无截止日期目标**（如「生活质量」）仅展示攒钱占比，不参与时间轴对照。
- 呈现示例：
  ```
  FIRE        ████████░░░░░░░░  42%  (时间轴应达 50% ↓落后2月 · 黄)
  生活质量    攒钱占比 35%  ·  本月已享 ¥1,200 / 基线 ¥2,500
  ```

**2. 近 6 个月资金流向 ASCII 趋势图**
- 以月度为横轴，分层展示**投资攒钱 / 计划生活消费 / 非计划冲动支出 / 安全垫红线**四层结构。
- 目的：让用户一眼看清「钱去哪了、攒钱节奏稳不稳、是否某月冲动超支」。
- **月度快照持久化**：每月末报表生成时追加一条快照进 `contract.json` 的 `monthly_history`，避免重复计算。
- **conversational 模式标注**：因无持久台账，趋势图标注「估算数据，精度有限」，不假装精准（与 §3 边界护栏一致）。
- 叠加「安全垫红线」：若某月 corpus 逼近 `effective_cushion` 则高亮告警。
- 呈现示例（ASCII 趋势）：
  ```
  攒钱 ████░ ████░ █████ ███░░ ████░ █████      ← 投资攒钱
  生活 ██░░░ ██░░░ ██░░░ ███░░ ██░░░ ██░░░      ← 计划内生活
  冲动 ░░░░░ ░░░░░ █░░░░ ░░░░░ ██░░░ ░░░░░      ← 非计划内冲动（3月/5月尖峰）
  月份  1月   2月   3月   4月   5月   6月
  ── 安全垫红线 ──────────────────────────
  ```

**实现要点**：
- 报表以「文字统计（资产池 / 分配 / 达成率 / 已批驳回 / 安全垫预警）+ 可视化（本模块）」双段呈现，可视化不替代数值，仅增强感知。
- 渲染优先文本 ASCII/Unicode 进度条与趋势图（webchat/desktop 均兼容）；若下游渠道支持富媒体，可升级为图片图表。

### 6.2 月度自动校准 rebalance（缓冲机制优化）

在 §2 目标权重基础上，新增**月度自动校准**：每月生成记账报表时，规则引擎自动校验各目标当前达成进度，无需用户手动改契约即可对齐长期目标。

**校准触发**：记账报表生成时（或 `contract.json` 中 `last_calibrate` 跨月）。

**校准缓冲期（防偶发波动）**：
- 单次月度落后**不直接触发**占比调整。需**目标连续 2 个月 `lag > 0`**（采用 **公式 4** 计算 `lag`），才正式写入 `rebalance_override`。
- 每个目标维护 `lag_streak`（连续落后月数，达标月归零）；仅当 `lag_streak >= 2` 触发 boost + 收紧。
- 目的：单月突发大额刚需（医疗 / 应急）导致临时偏离，不应过度收紧下月消费权限；偶发一次由安全垫 + 分期机制吸收。

**调整逻辑（柔性优先，不只有收紧）**：
- **柔性方案（优先采用，不损害用户体验）**：
  - 调低目标额：当 `lag_streak >= 2` 且差距主要源于客观环境变化，`rebalance_override` 写入 `target_amount` 下调建议（如按真实口径公式 7 反推可达成的数额），并提示「目标已据当前节奏柔性下调至 X，原目标可在收入恢复后手动调回」；
  - 延长期限：写入 `deadline` 顺延建议（如 +N 月），使时间进度重新对齐，避免为追原期限而过度压缩当下消费。
  - 柔性方案写入独立的 `rebalance_override`（不改动原始 `objectives.target_amount` / `deadline`），次月重评、达标或手动确认后回滚。
- **刚性方案（仅柔性不可行时）**：临时上调该目标**投资占比上限**（单次最高 **+15pct**）；同步**降低非计划消费审批通过率**（收紧护栏，具体降幅由 `lag` 深度映射）。

**收入下跌自动放松（反脆弱护栏）**：
- 监测**实际月度注入实绩**（`monthly_history[].income`，而非契约常量 `monthly_contribution`——静态配置不会逐月变化）相对基线（契约值或近 3 月实绩均值）的变动：若**连续 2 月下降 ≥ 20%**（或转负），自动进入「宽松态」——
  - `invest_ratio` 在 `rebalance_override` 中**临时下调**（如 −10pct），优先保 `living_baseline` 基础生活，不因为目标落后而挤压生存消费；
  - 暂停对「非计划消费审批通过率」的收紧，甚至适度放宽；
  - 报表高亮「收入下行，已自动放松储蓄比例，优先保障生活」提示，不制造焦虑。
- 收入恢复（连续 2 月回升至基线 ±10% 内）后，`rebalance_override` 自动回滚至常规校准态。
- 该放松**不破坏** `safety_cushion` / 原始 `invest_ratio` / `objectives` 字段，仅作用于临时层。

**约束**：
- 校准为**临时覆盖层**，写入 `contract.json` 的 `rebalance_override`，**不改动用户原始 `objectives.weight`**；次月重新评估，达标自动清空调整。
- 安全垫 `effective_cushion`（公式 1）优先级最高：任何校准后余额不得跌破安全垫（即调整后攒钱比例不可突破「保留安全垫后剩余可投」）。
- **报表强制提示**（必含）：标注本次调整**生效周期**（当月至下次月度校准前，仅本月有效）、**次月自动回滚**（重新评估，`lag_streak` 归零重计，原始权重不变）、**原始权重不变**。
  - 示例：「[临时校准] FIRE 连续2月落后，本月投资占比 +12pct、非计划内审批率降至 60%；本调整仅本月生效，次月自动重评，原始权重不变。」
- 报表显式列出：哪些目标被 boost、非计划内通过率降到多少、何时失效。

**效果**：「配置者」无需介入，「规则引擎」在合规护栏内自动纠偏，长期目标自对齐。

### 6.3 里程碑正向奖励机制（留存激励闭环）

**问题**：长期约束（冷静期 / 破垫驳回 / 校准收紧）易产生倦怠，用户需要「坚持有回报」的甜头，否则框架可能被弃用。
**方案**：当某目标**达成率 ≥ 120%**（累计额 ≥ `target_amount × 1.2`，视为超前超额完成里程碑），自动**解锁一笔「目标奖励额度」**，允许用户从超额部分支取最高 **20%** 用于**专项消费**，给长期坚持正向反馈。

**解锁条件**（采用 **公式 6**）：目标资产达成率 ≥ 120%，且 `reward_unlocked = false`（未领取过该阶段奖励）。
**奖励额度**：`reward_max = 超额资产 × 0.2`（上限 = 超额部分的 20%）。
**使用特权**：
- 用户通过 `记账奖励 <用途>` 支取，规则引擎核对 `reward_unlocked` 与剩余额度后批准（**仍走 §4.4 统一判定与安全垫校验**——与白名单同理：免等待，不豁免判定）；
- **免冷静期**（这是正反馈，不是冲动拦截）；
- **专项消费**，完整记录存入 `reward_log`（时间、目标、金额、用途）；解锁时在该 objective 写 `reward_quota = reward_max`（剩余可支取额），**支持分次部分支取**，每次支取递减，减到 0 即额度用尽（`reward_unlocked` 保持 true，不重复解锁）。
- **护栏约束**：奖励支取**不消耗基础生活费、不击穿安全垫**（来自超额，不影响原始护栏）。

**护栏约束（全链路）**：
- 单目标**仅解锁一次**基础奖励（`reward_unlocked` 标记后即便后续回撤不再重复发）；后续更高达成比例（150% / 200%）作为**扩展规划**另议，不在基础奖励范围。
- 奖励**不改变目标截止时间与权重**，仅是超额部分的回馈；安全垫 `effective_cushion` 优先级仍最高。
- 与 §5.1.1 撤回正向反馈、§6.1 进度条形成「克制有奖 / 超前重奖」的正向激励闭环，对抗长期约束倦怠。

**报表呈现**：进度条超 120% 时标「🏆 已解锁奖励 ¥X，可 `记账奖励` 支取」，强化成就感知。

### 6.4 目标生命周期（达成 / 超期 / 移除的闭环处理）

**问题**：目标只有「进行中」一种状态——达成 100% 后是否继续吸资、超期未达成怎么办、删目标钱去哪，全无定义，长期运行必然遇到。

| 状态 | 触发 | 处理 |
|---|---|---|
| `active` 进行中 | 默认 | 正常参与权重分配 / 校准 / 审批测算 |
| `completed` 已达成 | `current_amount ≥ target_amount` 且用户确认收尾 | 停止吸资；该目标 `weight` 释放，**提示用户重分配**（不自动改其他目标权重，遵守 §10.3 配置区只读）；进度条标 🎉；里程碑奖励逻辑照常（§6.3） |
| `overdue` 超期未达成 | 当前日期 > `deadline` 且达成率 < 100% | 退出 §6.2 常规校准（见公式 4 超期守卫）；报表高亮 + 给三选一：**延期**（改 deadline，过 §5.4 闸门）/ **降额收尾**（改 target_amount，过 §5.4）/ **确认放弃**（转 `archived`）；未选择前维持只读展示，不再收紧消费 |
| `archived` 已归档 | 用户显式移除 / 放弃 | 该目标累计 `current_amount` 归还资金池自由层（corpus 不变，仅解除目标锁定语义）；留 `approval_log` 归档记录；权重释放同 completed |

- 状态字段：`objectives[].status`（默认 `active`；schema 向后兼容，缺省视为 active）。
- 状态迁移全部**用户显式确认**（规则引擎只提示不代决），核心字段变更一律过 §5.4 二次确认。

## 7. 规则引擎优化目标（三档模式，全局调度开关）

`optimization_goal` 是规则引擎行为的**全局调度开关**，决定审批引擎（§4.4 / §5）、校准（§6.2）、合理享受额度、目标权重分配的默认倾向。三档可随时切换，默认值 `(b) balanced`。

| 模式 | 定位 | 行为特征 |
|---|---|---|
| (a) `wealth` 财富最大化 | 偏储蓄，长期资产积累优先 | **收紧非必要消费审批**（§4.4 场景 B 更严苛、场景 C 驳回更果断）；校准机制（§6.2）大幅倾斜资产积累——boost 幅度取上限、非计划消费审批通过率压到最低；合理享受额度压缩 |
| (b) `balanced` 均衡模式（**默认推荐**） | 储蓄与生活消费平衡 | 合理享受额度充足，允许在划安全垫（§2.1）前提下正常享受；储蓄与生活消费兼顾，长期目标与当下幸福感并重；校准按 §6.2 常态缓冲执行 |
| (c) `objective` 单一目标导向 | 资源集中打穿核心目标 | 所有资源倾斜指定核心目标（如 FIRE），**大幅压缩非目标类消费额度**；校准（§6.2）对该目标强倾斜，非目标审批近乎按场景 C 处理；合理享受额度最小化 |

**调度影响面**（统一由本开关驱动，不在各章节各自硬编码）：
- **审批阈值**：`wealth` 收紧 §4.4 场景 B/C 判定边界；`objective` 对非目标类消费额外收紧。
- **合理享受额度**：`balanced` 充足、`wealth` 压缩、`objective` 最小化（额度 = 安全垫余量内仅保基本生活）。
- **月度校准（§6.2）**：`wealth`/`objective` 取 boost 上限 + 通过率下限；`balanced` 维持缓冲默认。
- **意见书（§5.3）**：驳回/附条件时按当前模式陈述代价，措辞一致。

**切换纪律**：
- 模式切换为配置者显式指令（`记账模式 <wealth|balanced|objective>`），不自动改——保持配置者掌握开关（同 §3.1 平滑过渡纪律）。
- 切换仅改调度倾向，**不破坏**原始 `objectives.weight` / `safety_cushion` / 契约结构；`objective` 模式下的核心目标由用户指定，不自动改写其他目标。
- `objective` 模式需至少指定 1 个核心目标，未指定则退回 `balanced` 并提示。

设计为 `optimization_goal` 字段（schema 已含，默认 `balanced`），初始化（§7.1）固化默认值，后续可切。

### 7.1 初始化引导（懒人一键模板）

**问题**：§2 的完整 schema 字段多，首次 setup 门槛高。
**方案**：提供「懒人一键初始化模板」，用户**仅需输入 3 项**即可生成符合 `balanced` 默认目标的完整契约；其余参数由系统**统一固化**为 balanced 均衡型默认值（见下方推导表），后续再逐步自定义。

### 必填 3 项

| 输入 | 字段映射 | 说明 |
|---|---|---|
| 当前可注入资金池的总资产 | `corpus` | 资金池初始余额（支持手动填 / 第三方导入，见 §7.3） |
| 月均可支配收入 | `monthly_contribution` | 月度注入额；**按「税后收入 − 负债月供 − 刚性年支出月摊」净口径填**（见公式 0）；懒得细算可先填毛可支配额，后续用 `记账自定义` 补 `liabilities` / `rigid_annual_expenses` 修正 |
| 核心目标（1~3 个） | `objectives[]` | 每项：名称 + 目标额 + 期望达成日 |

> 说明：3 项为基础路径（手动填写）。`corpus` 另提供第三方记账工具一键导入的可选能力（见 §7.3），导入后仍走相同初始化流程。

### 系统统一固化默认参数（无需用户填）

> 初始化时以下参数**统一固化**为 balanced 默认值，不随用户输入变化；`living_baseline` 的三模式切换、`mode` 等其他自定义留待初始化后按需调整（见 §7.4 / §3）。

| 推导项 | 固化默认值 | 依据 |
|---|---|---|
| `living_baseline` | `mode=auto`，取值 = `monthly_contribution × 0.5` | 工薪现金流默认半额作生活费基线（§7.4 可后续切 manual/history3m） |
| `safety_cushion` | `{ mode: "months", months: 6 }` | 6 个月生活费垫（见 §2.1，随 baseline 联动） |
| `invest_ratio` | `0.5` | 注入额半仓投资 |
| `allowed_categories` | `[食品,居住,交通,通讯,医疗,教育,服饰,日用,合理享受,娱乐,旅行,社交,宠物,数码家电,保险,房产,车辆,投资,理财,基金,股票,黄金,其他]` | 标准类目词汇表（推荐清单，非硬约束；judge 不强制成员校验） |
| `mode`（数据模式） | `hybrid` | 混合开关（§3），初始即开台账+会话双源 |
| `optimization_goal` | `balanced` | 默认优化目标 |
| `cooldown_days` | `3` | 冷静期默认 3 天 |
| `objectives[].start_date` | 初始化当日 | 算时间进度用 |
| `objectives[].weight` | 均分（1/N） | 多目标等权起步，靠 §6.2 自动校准调整 |

**交互**：触发 `记账初始化` 或首次使用审批时引导；3 项填完即生成契约落 `<data-dir>/contract.json`（见 §8.3 #6 数据目录兜底），回复「已生成默认契约，可随时说『自定义』逐项调」。后续自定义不破坏已填值（增量覆盖）。

**初始化护栏（防止覆盖 / 虚高 / 脏数据）**：
1. **重复初始化防护**：落库前检测 `<data-dir>/contract.json` 是否已存在。已存在则**拒绝整文件重写**，回「已存在契约，增量修改请用 `记账自定义`；如需彻底重建请用 `记账重置`（带二次确认，且保留 audit 目录历史）」。初始化路径不绕过 §10.3 三区权限——契约属配置区，必须经 `记账自定义` 闸门或 `记账重置` 显式重建，禁止静默覆盖。
2. **净口径警告**：若用户未按净口径填 `monthly_contribution`（即填了毛可支配额，未补 `liabilities` / `rigid_annual_expenses`），回执末尾加 ⚠️「当前 `monthly_contribution` 为毛口径，`living_baseline` / `safety_cushion` 据此偏高，建议尽快 `记账自定义` 补负债/刚性支出」。
3. **目标 deadline 校验**：`objectives[].deadline` 必须晚于 `start_date`（=当日）；填错或早于当日则驳回该项并提示重填，不生成负周期。
4. **对账锚点初始化**：init 顺手设 `reconcile.last_reconcile = 初始化当日`，使 §3.2 的 30 天对账窗口从首日起算，边界清晰。

**效果**：零配置上手，默认值全部指向 `balanced` + 安全垫护栏，先跑起来再精调。

### 7.1.1 契约重建（`记账重置`）

**问题**：§7.1 护栏 1 禁止 `记账初始化` 覆盖已有契约，但用户确有「推倒重来」需求（如首次填错、想换目标体系）。
**方案**：提供 `记账重置` 作为**唯一**整文件重建入口，与初始化分离，且带更强护栏：
- **二次确认**：首次说 `记账重置` → 回「将丢弃当前契约并重建，audit 历史保留。确认请再说一次『确认重置』」；收到确认才执行。
- **不抹审计**：仅重写 `contract.json`，`<data-dir>/audit/` 下全部日志（审批/申诉/覆写/奖励/月度）**原样保留**，符合 §10.1 仅追加不可删。
- **重建留痕**：在 `override_log` 记一条 `event=contract_reset` 事件（含旧契约哈希摘要、重置时间、触发原因），使「推倒重来」本身也可复盘，不破坏审计链。
- **权限等价**：`记账重置` 与 `记账自定义` 同属配置区写操作，受 §10.3 三区权限约束（需配置者显式指令，引擎不可自启）。
- **重置后**：回到 §7.1 懒人模板流程，3 项重填；已保留的 audit 历史中若引用旧 `objective_id`，在报表中标注「（已重置前）」以免混淆。

### 7.2 初始化配套模拟演示（优化交互）

首次完成懒人初始化（`记账初始化` 落库成功）后，**自动输出 3 类标准场景模拟测算**，用初始化生成的真实契约参数推算，**不落地真实账目**，让用户无需自行摸索即理解框架运行逻辑；支持随时 `记账演示` 重看。

**3 类标准场景**：

| # | 模拟场景 | 触发规则 | 演示结果 |
|---|---|---|---|
| 1 | 小额合理消费（如喝奶茶 35 元，类目「合理享受」） | 金额 < `effective_cooldown_threshold` 且不破垫 | **直接批准**——展示「计划内享受额度充足，走 §4.4 场景 A 放行」 |
| 2 | 大额非计划消费（如买新款手机 6000 元，非计划内） | 金额 > `effective_cooldown_threshold` | **触发 3 天冷静期**——展示「已触发冷静期（§5.1），第1天提醒+到期前二次确认，可撤回」 |
| 3 | 击穿安全垫大额消费（如奢侈品包 3 万元，非计划内·破垫） | `corpus - 支出 < effective_cushion` | **驳回 + 分期替代方案**——展示 §5.3 意见书：契约对照 / 目标延后时长 / 「分 N 月从合理享受额度支取」替代路径 |

**交互**：初始化完成回复末尾附演示区块（含上述三格），并提示「这是演示，不影响真实账户；现在可以说『审查：买X花Y』开始真实审批」。随时 `记账演示` 重看。

**效果**：把抽象的 **§4.4 统一判定逻辑**、§5.1 阈值、§5.1 冷静期、§5.3 意见书一次性具象化，零成本建立认知。

### 7.3 第三方资产导入能力（数据校验硬约束）

除手动填写 `corpus` 的基础路径外，提供**第三方记账工具 / CSV 导入**的可选能力；导入后**强制人工核对校验**，避免原始数据偏差污染后续所有审批决策。

**流程**：
1. 用户触发 `记账导入 <工具名>`（如随手记 / 钱迹 / 自定义 CSV）。
2. skill 拉取账户余额 / 近月流水，自动算出 `corpus` 候选值（及可选 `monthly_contribution` 均值）；若源数据含负债与刚性年度支出，一并拉取 `liabilities` / `rigid_annual_expenses` 候选清单供核对。
3. **人工核对步骤（必过）**：列出导入摘要（总资产、近3月净流入、可疑流水），请用户**逐项确认 / 修正**后才写入 `contract.json`。
4. 核对确认后，`corpus_status` 由 `imported_pending` 切换为 `imported_confirmed`，资产池正式生效，方可进入审批。

**数据清洗（2026-07-28 H1 修复）**：拉取的余额行先按 `(账户名, 类型)` 去重合并——完全重复行（余额/月供全同）静默丢弃，同名异额行求和并列入 `warnings` 告警，杜绝同一账户在源数据重复列出导致资产/负债被双倍计入。`provided` 标记区分「来源实际提供了哪些分类」，确认时仅覆盖显式分类、缺类保留 live 原值。

**状态机（契约硬约束）**：
- `imported_pending`：导入已拉取但尚未人工核对确认；**禁止任何支取审批**（§4.4 判定入口前置拦截），避免未经核实的资产污染决策。
- `imported_confirmed`：用户修正确认后生效，资产池正式纳入资金池，后续审批流程正常。

**约束**：
- 导入仅作为「数据来源通道」，不替代自律纪律；核对校验是硬门槛，跳过则不允许启动审批。
- 不自动采信：导入数据可能含重复账户、未剔除负债、币种错配等，须用户拍板；可疑流水须在核对步骤显式处置。

> **状态**：已实装（2026-07-28，[0.7.0] `scripts/modules/import_asset.py` + `cli.py import-asset`；[0.7.1] 导入语义收敛；[0.7.7] M1–M3/M6 健壮性）。候选先暂存于 RUNTIME 区 `pending_import`（`corpus_status=imported_pending`，锁定全部审批），人工核对确认（token 防漂移）后才落到 live `corpus` / `monthly_contribution` / `liabilities` / `rigid_annual_expenses`（`imported_confirmed`）；`--cancel` 还原 prior_status 不污染 live 资产。详见 STATUS.md `[0.7.0]` / `[0.7.1]` / `[0.7.7]`。
>
> **[0.7.7] 健壮性增强**：① 同名账户 `(账户名,类型)` 去重合并（完全重复丢弃、异额求和告警，H1）；② 金额容忍币种符号 `¥$￥` 与千分位逗号、流水日期支持 `年-月-日/年/月/日/年.月.日/年-月`（M2）；③ rigid 行解析可选 `due_month` 列（1–12）透传到期月，不再恒 None（M3）；④ 确认时 `liabilities`/`rigid_annual_expenses` 修正按 name 合并（覆盖同名 + 保留未提及项），不再整表覆盖丢数据（M6）。
>
> **导入语义（[0.7.1] 收敛，消除 footgun）**：区分两种用法——
> - **CSV = 完整快照**：余额表须列齐资产 / 负债 / 刚性，`confirm` 以候选**全量重基线** live（缺类 = 该分类归零，故表不能只传一部分）；
> - **手动 = 局部修正**：`--corpus / --liabilities / --rigid` 只传想改的项，`confirm` 仅覆盖显式传参分类，其余 live 原值保留。
>
> 底层 `compute_candidates` 对每类打 `provided` 标记、`confirm_import` 只覆盖「来源显式提供」或「人工修正(corrections)」的分类；旧契约无 `provided` 标记时回退为全量覆盖（兼容）。**彻底消除「CSV 缺某类 → 静默清空 live 负债 / 刚性」的数据丢失风险**。

### 7.4 月度生活费基线分层（三模式）

`living_baseline` 由单一推导升级为**分层选项**，适配不同消费习惯：

| 模式 | 取值 | 适用 | 校准性 |
|---|---|---|---|
| `auto` 自动（默认） | `monthly_contribution × 0.5` | 收入稳定、无明显消费周期 | 随注入额联动 |
| `manual` 手动固定 | 用户填固定额 | 消费额刚性、想自己定线 | 不变，手动调 |
| `history3m` 历史均值 | 近 3 个月历史平均消费 | 消费波动大、想按真实习惯 | 每 3 月重算一次 |

- 默认 `auto`；初始化后可随时切（增量覆盖）。
- `history3m` 需有导入或 ledger 记账数据支撑，无历史时回退 `auto`。
- 安全垫 `months` 模式随 `living_baseline` 自动联动（见 §2.1），基线一变垫跟着变。

## 10. 风险防控与数据安全（落地必备模块）

### 10.1 全链路审计留痕（不可删除）

所有关键动作**永久持久、仅追加、不可删除**：
- 审批日志 `approval_log`（§4.4/§5）：每笔审批决策留痕（时间/金额/类目/场景/判定摘要），并附**完整计算中间变量快照**（公式 0/1/3/3.5/4/7 全部输入与中间值，见 公式 8），支持事后逐式复盘验算。
- 申诉日志 `appeal_log`（§5.2）：每次申诉/驳回/人工复核结果留痕。
- 覆写日志 `override_log`（§5.2）：人工复核 override 留痕（时间/金额/目标影响/确认）。
- 月度快照 `monthly_history`（§6.1）：近 6 月资产与消费分配快照。
- 奖励支取 `reward_log`（§6.3）：里程碑奖励用途留痕。
- 申诉记录：每次申诉/驳回/人工复核结果留痕（§5.2）。

**硬约束**：审计数据**只增不删、不提供删除接口**；撤回/覆写等行为以「追加反向记录」表达，而非抹除原记录，保证全链路可追溯。

### 10.2 极端场景兜底

| 极端场景 | 触发条件 | 兜底行为 |
|---|---|---|
| 资金池接近安全垫 | `corpus` 逼近 `effective_cushion`（如余量 < 1 个月生活费） | 报表（§6.1）**高亮红色预警**；临时**自动收紧非计划消费**——§4.4 场景 B/C 判定边界收紧、通过率压低（等同临时进入更严审批态，不改变 `optimization_goal`） |
| 长期无收入注入 | `monthly_history` 连续 N 月 `monthly_contribution` 为 0 | **暂停 §6.2 校准加权重分配**，优先保障 `living_baseline` 基础生活基线；不因为目标落后而挤压生存消费 |

### 10.3 权限隔离（规则引擎最小权限）

规则引擎遵守**最小权限**（契约三区划分，消除「只读契约却要写计数器」的矛盾）：
- **配置区只读**：`objectives` / `safety_cushion` / `invest_ratio` / `optimization_goal` / `calc_params` / `distribution_rules` 等原始配置字段，引擎无写权限，仅配置者经 `记账自定义`（过 §5.4 闸门）可改。
- **运行态区可写**：计数器与临时层（`lag_streak` / `appeal_count` / `used_annual` / `report_streak` / `gap_streak` / `rebalance_override` / `last_*` / `reconcile.*` / `pending_spends` / `pending_import` / `pending_config_changes` / `pending_requests`）由引擎按既定规则更新，均不改变配置区语义。
  - `pending_spends`（[0.7.7] M4）：审批通过的支出台账（运行时态）。`corpus` 属配置区、引擎最小权限**不可自动改写**，故审批不自动扣 corpus——改为把实际现金流出记入 `pending_spends`，`governance.reconcile` 对账时并入并清空（返回 `pending_spends_cleared`），消除「审批通过不扣账」的静默坑。
- **审计区仅追加**：`approval_log` / `appeal_log` / `override_log` / `reward_log` / `monthly_history` 落 `<data-dir>/audit/` 独立文件，只增不删（§10.1）。
- **无权修改**用户原始配置：目标权重、安全垫、基线等只可通过 `记账自定义` 由配置者显式改；§6.2 校准写入独立的 `rebalance_override` 临时层（不改原始 `weight`），§5.2 覆写写入 `override_log`（不抹原契约），均不破坏原始字段，符合权限隔离。

### 10.4 数据本地持久与隔离

- 所有契约、台账、日志存储于**用户独立 `<data-dir>` 空间**（默认 `<home>/.claw/self-trust`，规范 §3 平台基址锚定不赖 cwd，可被 `--data-dir` / `SELFTRUST_DATA_DIR` 覆盖，优先级命令行 > env > 默认，见 §8.3 #6）。默认 `self-trust/` 目录位于 **`.claw` 备份树内**（MA-2 备份覆盖）且在 **skill 目录外**（删除/重装 skill 不毁账本，§10.1 永删留痕前提）。
- **数据隔离不互通**：每个配置者（用户）独立命名空间，跨用户/跨会话不共享、不串读。
- 持久化与 §3 数据模式解耦：ledger/conversational/hybrid 只影响采集方式，最终状态统一落 `<data-dir>/`（默认 `<home>/.claw/self-trust/`，可覆盖），保证单点真相。

**落盘健壮性（[0.7.15] 三层加固）**：`contract.json` 写入路径为**原子写**（唯一临时名 `contract.<pid>.<tid>.<uuid8>.tmp` + `os.replace` 整文件替换），并对写入内容**回读校验**（明文 `json.loads` / 密文 `unseal_json`），校验通过才替换、失败瞬态重试（≤3 次）且不破坏原好文件；读取时若检测到**拼接 / 截断 JSON**（写入中途被打断遗留的残缺文件），抛 `ContractCorruptedError` 并指向 `contract.json.bak.corrupt` 恢复路径，绝不裸抛 `Extra data`。**运维铁律**：任何命令报 `Extra data` / `request_not_found` 须**停手上报、勿重跑**——重跑可能把已修复文件又写花。

### 10.5 静态加密（数据静态加密 at rest，opt-in）

**问题**（[0.7.14]）：本地账本（资产 / 负债 / 消费习惯）明文存 `<home>/.claw/self-trust/`，可能被云同步（OneDrive / iCloud / 百度网盘）误带上云，个人完整财务画像泄露风险。

**方案**：契约（`contract.json`）与审计日志（`audit/*.jsonl`）支持 **AES-256-GCM**（AEAD 认证加密，防篡改）静态加密落盘。**opt-in，默认关**——未启用时读写行为完全不变，向后兼容明文契约。

**两条密钥路线（初始化时一次性决定，之后不可原地切换）**：
- `passphrase`（默认）：用户口令，每次命令 `--pass <密码>`（或环境变量 `SELFTRUST_PASS`）；密钥由口令经 **PBKDF2-HMAC-SHA256（20 万轮）** 派生，**从不落盘**；口令丢失 = 数据不可解密。
- `key-file`：首次 `init --encrypt --crypto-mode keyfile` 自动生成 `<data-dir>/.self-trust.key`（**权限 600**），后续命令自动定位、无需每次传参；密钥文件丢失 = 数据永久不可解密，须单独备份。

**文件格式与透明兼容**：密文 = `MAGIC(STENC1\n) + 模式字节(P/K) + salt(仅 P) + nonce(12) + ct`；`is_encrypted` 魔数检测，存储层透明加解密（读明文契约走 `json.loads`、读密文走 `unseal_json`）。口令错误 → GCM tag 校验失败抛 `InvalidPassphrase`，引擎返回清晰错误（exit 5），**不静默用明文读写**。

**依赖**：仅加密路径需可选依赖 `cryptography`；非加密路径纯标准库零依赖。未安装时引擎返回 `加密功能需安装 cryptography：pip install cryptography`。

**设计约束**：
- 切换加密状态（开→关 / 换路线）需 `reset --confirm` 后重新 `init`，现有契约不原地改密；
- 加密**不改变 §10.1 审计「仅追加不可删」语义**，仅把追加内容转为密文——审计完整性在加密态下依旧成立。

## 11. AI 规则引擎公正性保障体系（中立、客观、可审计的强制约束）

> 本 §11 不是新增规则，而是把前文分散的护栏（§1 流程隔离 / §2.0 公式 / §3 数据中立 / §4.4 判定 / §5 制衡 / §6.2 缓冲 / §6.3 激励 / §7 开关 / §10 审计）收敛为一套**公正性保障闭环**，回答一个核心问题：**AI 规则引擎的公正、客观如何被强制保障，而非依赖 AI 主观道德**。
>
> 设计信条：**公正性不靠 AI 自我约束，而靠「权责隔离、统一标准、可审计、人工兜底、中立调度、数据中立」六大体系强制约束**，从架构上消除主观偏袒、情绪化松严、双重标准。

### 11.1 底层权责隔离：从权限上杜绝 AI 主观改规则

**最小权限原则**（对应 §10.3）：
- 规则引擎对契约实行**三区权限**（§10.3）：配置区（安全垫、目标权重、消费类目、冷静期等）只读；运行态计数器与临时校准层 `rebalance_override` 可写；审计日志仅追加——**不能直接修改**用户原始参数；
- 所有核心规则（安全垫模式、月度基线、投资比例、目标权重）**仅配置者**通过 `记账自定义` 手动修改，AI 仅提供建议、无变更权限。
- 意义：规则由用户提前白纸黑字定义，AI 只是执行者，不存在私自放宽 / 收紧标准的空间。

**三方角色隔离**（对应 §1）：
- 框架把人拆为配置者（现在的我）与未来的你（现在+未来的我）；AI 规则引擎按既定纪律规则**强制优先保护长期未来的你利益**，而非迎合当下短期诉求；
- 长期优先原则明确：无论用户反复强调「就这一次」，引擎只按数学指标判定，不受情绪话术干扰；
- 资金流程隔离（§1，软件内流程约束）：资产入池后无直接支取通道，所有支出统一走审批，AI 不能私下放行。

### 11.2 全局唯一统一判定标准：消除双重标准

1. **全场景复用同一套判定逻辑（§4.4）**：日常消费、大额冲动、医疗应急、奖励支取、人工覆写，不分类型、不分金额，全部共用三段式判定（场景 A 放行 / B 附条件 / C 驳回）。所有输出仅由 `corpus`、支出金额、安全垫、目标落后度 `lag` 四个客观数值决定，无模糊主观打分。
2. **全部依赖标准化数学公式（§2.0）**：8 套公式硬编码（净资产/安全垫/冷静期阈值/月度可投增量/通胀回撤修正/目标落后度 lag/真实口径测算/审批审计快照），纯数值运算，无人工裁量；所有审批结论、收紧力度、校准幅度均由数字输出。
3. **全局调度开关标准化（§7）**：`optimization_goal` 三档（wealth/balanced/objective）由用户**显式手动切换**，AI 不自动切换松紧；不同模式审批收紧、校准幅度有固定量化规则；报表标注当前模式与幅度，临时校准仅存 `rebalance_override`、次月回滚，松紧变化全程可查。

### 11.3 冷静期 / 白名单 / 申诉三层制衡：平衡刚性与公平

1. **冷静期（§5.1）**：大额非刚需支出强制 3 天冷静期 + 两次提醒 + 允许撤回；撤回不改判定规则、仅给 §5.1.1 正向激励；冷静期仅延迟执行、不修改底层逻辑。
2. **极速白名单（§5.1.2）**：医疗 / 急诊 / 房屋应急等刚需仅免冷静等待，**不豁免安全垫与统一判定**；类目由用户手动增删、写入契约；应急支出同样校验资产底线，无隐形偏袒。
3. **人工覆写兜底（§5.2）**：连续 3 次申诉驳回后开放一次性人工复核；覆写前须阅读并确认本次消费对长期目标的量化延后代价；所有破例存入 `override_log`、月度报表单独公示；单次覆写消耗申诉计数，需重新积累 3 次，兜底是例外非常态。

### 11.4 全链路不可删除审计（§10.1）：所有决策可复盘

- `monthly_history` / `override_log` / `reward_log` / 申诉记录**仅追加、不可删除、不可篡改**；
- 标准化意见书（§5.3）三段固定内容：契约数值对照 / 量化目标影响 / 客观替代方案，**不出现 AI 主观评价、情绪化说教**；
- 可视化报表（§6.1）公开所有变量（安全垫余量、目标进度、冲动占比、校准幅度），用户可自行复算验证 AI 判定。

### 11.5 数据中立机制（§3 / §7.3）：消除数据偏差导致的不公

- 三类数据模式边界清晰、缺陷主动标注：conversational 无持久台账→每次审批强制确认总资产；ledger 缺流水→报表标注「数据不全，测算存在偏差」，不输出虚假客观；
- 第三方导入（§7.3）强制人工核对：`imported_pending` 锁定、禁止审批，用户逐项修正确认才生效；
- 生活费基线三模式（§7.4）规则固定、由用户自选，同一模式下所有消费用同一基线标准，不双标。

### 11.6 校准缓冲机制（§6.2）：防单次突发过度收紧

- 月度自动校准**连续 2 个月落后**才触发，单月突发医疗 / 应急不致立即收紧；
- 触发仅临时上调投资比例、收紧非计划消费，写入 `rebalance_override`，**次月自动回滚、原始权重不变**；
- 避免 AI 因单次意外过度严苛，实现短期刚需与长期储蓄的客观平衡。

### 11.7 激励体系中立（§5.1.1 / §6.3）：奖惩统一量化

- 撤回冲动消费统一换算目标提前时长，无论金额 / 类型用同一公式给正向反馈；
- 里程碑奖励统一标准：达成率≥120% 解锁超额 20% 额度、单目标仅一次，规则无弹性；
- 激励全部基于客观数值，不凭 AI 主观判断「这次值得、那次不算」。

### 11.8 公正性保障闭环总结

| 公正维度 | 保障机制 | 对应章节 |
|---|---|---|
| 规则中立 | 用户提前定义，AI 无修改权限（最小权限 + 三方隔离） | §1 / §10.3 |
| 判定统一 | 全场景一套客观数值逻辑，无双标 | §4.4 / §2.0 |
| 权责制衡 | AI 仅执行者；用户拥规则修改 + 人工破例最终权（修改护栏须二次确认防冲动） | §1 / §5.2 / §5.4 |
| 全程可审 | 决策 / 破例 / 松紧调整 / **每笔审批完整计算中间变量**永久留痕、可复盘验算 | §10.1 / §5.3 / §6.1 / 公式 8 |
| 容错缓冲 | 冷静期 / 申诉 / 校准缓冲解决机械不公 | §5.1 / §5.2 / §6.2 |
| 数据可信 | 缺陷主动披露 + 外部数据强制校验 | §3 / §7.3 / §7.4 |

> 总结：引擎公正性完全由**标准化代码与数学公式**保障，而非依赖 AI 自身「道德判断」——从根源消除主观偏好、情绪化松严、隐形双标。
