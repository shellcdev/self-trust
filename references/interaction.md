# interaction — 用户交互规则（自然语言 → 引擎命令）

> 本文件定义 LLM 把用户自然语言转化为引擎命令时的**预处理与上下文规则**。
> 引擎是确定性代码，不会"猜"——所有模糊性由 LLM 在调用前消解。
> 全局参数（--data-dir / --today / JSON 输出）见 SKILL.md。

---

## 1. 上下文继承（request_id 记忆）

冷静期操作（撤回/确认/申诉/覆写）需要 `--request-id`，用户几乎不会主动报这串哈希。

### 规则

| 用户说的 | LLM 怎么拿 request_id |
|---|---|
| 「撤回」「确认那个」「申诉」（同会话、无 ID） | 用**本会话上一轮 judge submit 返回的** `request_id` |
| 「撤回那个手机的」「确认昨天那个包」（描述特征） | 先跑 `judge --action reminders`，按 `category` + `amount` 匹配；命中唯一 → 直接用；命中多条 → 列出让用户选 |
| 跨会话（"上次那个申请"） | 必须跑 `reminders` 或 `log --name approval_log` 查找；找不到 → 告知用户"未找到匹配的冷静期申请" |
| 用户直接给了 ID | 原样使用 |

### 记忆锚点（渲染时）

凡是向用户展示 `request_id` 的地方，**始终附带记忆锚点**，方便后续引用：

```
编号 e822534506c8（数码 ¥6,000.00）
```

格式：`编号 {request_id}（{category} ¥{amount}）`

> 这样用户下次说"撤回那个数码的"，LLM 也能从上下文锚点快速匹配。

## 2. 类目模糊映射

引擎 `--category` 接受自由文本不报错，但非标准类目会导致报表统计碎片化（"吃饭"和"食品"变成两个独立类目）。

### 映射表

| 用户可能说的词 | 映射到标准类目 |
|---|---|
| 吃饭/外卖/午餐/晚餐/早餐/夜宵/零食/饮料/奶茶/咖啡/水果/菜 | 食品 |
| 房租/物业/水电气/水电/燃气/网费/宽带 | 居住 |
| 打车/地铁/公交/停车/油费/高铁/火车/机票/滴滴 | 交通 |
| 话费/流量/套餐 | 通讯 |
| 看病/吃药/体检/牙科/挂号/医药 | 医疗 |
| 上课/报班/书/学费/培训/课程/考试 | 教育 |
| 买衣服/鞋/包/化妆品/护肤/穿搭 | 服饰 |
| 纸巾/洗衣液/日用/清洁/牙膏/洗发水 | 日用 |
| 电影/游戏/会员/视频/音乐/演出 | 娱乐 |
| 旅游/出行/酒店/机票/玩 | 旅行 |
| 聚餐/请客/红包/送礼 | 社交 |
| 猫粮/狗粮/宠物/ vet/兽医 | 宠物 |
| 手机/电脑/耳机/键盘/家电/电视/相机 | 数码家电 |
| 保险/保费 | 保险 |
| 基金/股票/理财/黄金/定投 | 投资类（按具体：基金/股票/黄金/理财） |

### 规则

1. 用户说的词**命中映射表** → 用标准类目调引擎，**不需要告知用户"已映射"**（静默归一）
2. 用户说的词**未命中** → 原样传入引擎 + 在输出末尾追加：「未归入标准类目，如需归入某类可告诉我」（轻提示，不阻塞）
3. 用户**显式说了标准类目名** → 直接用，不映射
4. 标准类目 23 项：食品/居住/交通/通讯/医疗/教育/服饰/日用/合理享受/娱乐/旅行/社交/宠物/数码家电/保险/房产/车辆/投资/理财/基金/股票/黄金/其他

> **原则**：映射是统计归一手段，不改变判定逻辑。引擎对 category 不做强校验（自由文本），映射只影响报表可读性。

## 3. 引导式初始化（onboarding）

新用户说「记账」「自律记账」「初始化」但没给参数时，**不要直接报"请提供 corpus"**，走引导流程：

### 三步引导

| 步骤 | 问什么 | 映射到参数 | 备注 |
|---|---|---|---|
| 1 | 「你目前手头有多少可用资金？」 | `--corpus` | 指流动资产（存款/余额宝等），不含房产 |
| 2 | 「每月能稳定存下多少？」 | `--monthly` | 净口径（扣除房贷/刚性支出后的可支配结余） |
| 3 | 「有什么长期目标？比如存够多少钱、什么时候要用？」 | `--objective` | 格式 `名称:目标额:期限`，可 1~3 个 |

### 执行

- 三项齐了 → 组装 `init` 命令执行，回执附 demo 干跑
- 用户一次给了多项（"我有20万，每月存8千，目标是FIRE 300万到2036年"）→ 直接组装执行，不走引导
- 用户只缺一项 → 只问那一项，不重复已知的
- 目标不会写 → 给示例：`FIRE:3000000:2036-01-01`（名称:金额:日期）

## 4. 金额自然语言解析

用户说金额时可能用中文数字或简写，LLM **应该解析**为阿拉伯数字再传引擎。

### 规则

| 用户说的 | 解析为 |
|---|---|
| 六千 / 6k / 6K | 6000 |
| 一万二 / 1.2w / 1.2W | 12000 |
| 两百 / 2百 | 200 |
| 三万五 / 3.5w | 35000 |
| 一百万 / 100w | 1000000 |
| 五十块 / 50块 | 50 |

> 这是 LLM 本身的能力，只需明确「**允许且应该解析**」。解析后不需要告知用户"已解析"。
> 无法确定时（如"几千块"模糊值）→ 询问用户确认具体金额。

## 5. 计划内标记推断（--planned）

`--planned` 标记影响是否触发冷静期（计划内支出豁免 F2 冷静期）。用户不会主动说"这是计划内的"。

### 推断规则

| 用户表述信号 | 推断 --planned | 理由 |
|---|---|---|
| 房租/物业/保险/学费/还贷/定期/续费/年费/月供 | `--planned` | 周期性刚性支出，已纳入预算 |
| 冲动/突然/想买/种草/拔草/手痒/忍不住/看到了 | 不传（默认 false） | 冲动性消费，正是冷静期要拦的 |
| 计划了很久/攒了钱买/预算内的/早就想买 | `--planned` | 有预算规划的支出 |
| 不确定 / 无明确信号 | 不传（默认 false） | 保守口径，让引擎走完整流程 |

### 规则

- 推断为 planned → 直接加 `--planned`，**不需要告知用户"已标记为计划内"**（静默推断）
- 推断为非 planned → 不加参数
- 用户**显式说**"这是计划内的"/"预算里的" → 加 `--planned`
- 用户**显式说**"冲动消费"/"临时起意" → 不加
- 推断依据应可在用户质疑时解释（"你提到房租，我标记为计划内支出"）

## 6. 主动冷静期提醒

不要等用户问，在相关时机**主动检查**冷静期状态。

### 触发时机

| 时机 | 动作 |
|---|---|
| 用户说「审查」「记账」「报表」类话题（会话开场） | 先跑 `judge --action reminders` 检查是否有 pending cooling |
| 审批输出后（judge submit 返回） | 如果 `cooldown.triggered=false` 但引擎返回的 JSON 里有其他 pending → 追加一行提示 |
| 用户说「撤回」「确认」但没给 ID | 跑 `reminders` 列出所有 pending 供选择 |

### 提示格式

审批后追加（仅当有其他 pending 时）：

```
⏰ 你还有 {N} 笔冷静期申请在等待（说「记账提醒」查看详情）
```

会话开场检查到 pending 时：

```
⏰ 你有 {N} 笔冷静期申请挂起：
· {category} ¥{amount}（剩余 {days_left} 天，编号 {request_id}）
· ...
```

> **省略条件**：reminders 返回空数组时不输出任何提示（不刷存在感）。

## 7. 多笔审批

用户一次说多笔支出（"买手机 ¥6000 和耳机 ¥800"）。

### 处理策略

1. **逐笔调 `judge`**（各自独立判定，引擎不支持批量）
2. **汇总渲染**：按场景合并输出，共享头部（资金池余额/月可用），各笔独立判定结论

### 渲染格式

```
📋 多笔审批（{N} 笔）：
· {category1} ¥{amount1} → {decision1.result} {decision1.summary}
  {cooldown1.triggered?⏳ 冷静期 {cooldown1.days} 天（编号 {request_id1}）:}
· {category2} ¥{amount2} → {decision2.result} {decision2.summary}
  ...
```

- 各笔的冷静期/白名单/目标影响**独立展示**
- 资金池余额用**最后一笔扣减后**的 `remaining_after`（反映累计影响）
- 如果某笔是 C（驳回），仍展示替代方案，但不影响其他笔的判定

> **边界**：超过 5 笔时建议用户分批（"一次审批太多笔，建议分 2~3 次说"），避免输出过长。

## 8. 多币种消费识别

用户消费时可能使用外币（出差/海淘/旅行），需要识别币种并传 `--currency` + `--rate`。

### 识别信号

| 用户表述 | 识别币种 | 传参 |
|---|---|---|
| `$200` / `200美元` / `200刀` | USD | `--currency USD --rate {当前汇率}` |
| `€100` / `100欧元` | EUR | `--currency EUR --rate {汇率}` |
| `HK$500` / `500港币` | HKD | `--currency HKD --rate {汇率}` |
| `£50` / `50英镑` | GBP | `--currency GBP --rate {汇率}` |
| `1000日元` / `¥1000`(日本语境) | JPY | `--currency JPY --rate {汇率}` |
| 无符号 / `¥` / `元` / `块` / `RMB` | CNY | 不传（默认） |

### 汇率获取规则

1. **用户主动报汇率**（"汇率7.2"）→ 直接用
2. **用户没报汇率但说了外币** → **必须询问**当前汇率（不猜、不查网络）
   - 询问话术：「这笔消费的汇率是多少？（如 USD→CNY 当前约 7.25）」
3. **用户说"按今天的汇率"** → 仍然询问具体数值（引擎需要确定数字，不接受"今天汇率"这种描述）

### 规则

- 币种与基准币种相同（如 contract=CNY, 消费=CNY）→ **不传** `--currency` / `--rate`（向后兼容）
- 币种与基准币种不同 → **必须同时传** `--currency` 和 `--rate`（缺一不可）
- 渲染时双显原始金额 + 换算后金额（见 rendering.md §0.4）
- `--rate` 是「消费币种→基准币种」的方向（USD→CNY 7.25 = 1美元换7.25人民币）

> **铁律**：汇率必须由用户提供具体数字，LLM **不自行估算汇率**（汇率波动大，估错会导致判定失真）。

## 附：交互规则速查

| 场景 | 规则 | 影响 |
|---|---|---|
| 用户没给 request_id | §1 上下文继承 | 减少 ID 记忆负担 |
| 用户说非标准类目词 | §2 类目模糊映射 | 报表统计归一 |
| 新用户没给 init 参数 | §3 引导式初始化 | 降低上手门槛 |
| 用户说中文数字/简写 | §4 金额解析 | 无需用户换格式 |
| 用户描述消费性质 | §5 planned 推断 | 冷静期正确触发/豁免 |
| 会话开场/审批后 | §6 主动提醒 | 冷静期不遗漏 |
| 用户一次说多笔 | §7 多笔审批 | 批量处理不丢笔 |
| 用户用外币消费 | §8 多币种识别 | 正确换算判定 |
